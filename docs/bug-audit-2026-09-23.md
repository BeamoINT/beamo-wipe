# Beamo Wipe bug audit — 2026-09-23

Base: `61846076cb83d3ed10fd5cde9c5a4a4dfc161668` on
`safety/windows-gpt-contents`. These changes are uncommitted pending the
required hosted ISO gate. All device tests used fake disk data; no erase was
run on hardware.

## Reproduced and fixed

Each case had a failing regression test before its implementation changed.

1. A stale `bootfrom=LABEL=BEAMO_WIPE` on a small internal disk could identify
   that disk as boot while a USB disk remained selectable. Boot discovery now
   rejects the ambiguous competition.
2. All-zero WWNs could alias unrelated disks to the boot device and could be
   used as confirmation identity. Boot alias and confirmation logic now ignores
   that padding value.
3. Final write progress at 100% could be reported as verified for a method
   that requires read-back. The progress fallback now requires a final
   verification phase for those methods; Quick zero remains unverified.
4. The report exporter decoded a wider log tail than the completion checker.
   A UTF-8 character split at the completion tail boundary made an unchanged
   log appear unavailable. Export now authenticates the exact completion tail.
5. A proven pre-spawn engine error left the recovery journal armed while the
   wizard offered a retry. The journal returns to preflight only after the
   runner proves no process was spawned and its wipe lock is quiescent.
6. A Tk refresh worker that failed to start left the wizard stuck in the
   refreshing state. It now ends the refresh with a visible error.
7. A failed real-engine spawn kept the sleep inhibitor active. The failed
   spawn path now stops it while releasing the wipe lock.
8. The cmdline ambiguity check still exposed a possible live USB when a
   USB-SATA bridge reported `tran=sata` like a small internal disk. With no
   resolved live mount, another plausible live medium now blocks selection;
   a resolved mount still allows the small fixed target.
9. A different boot USB could take the same `/dev` path before launch without
   failing the boot identity check. The wizard now compares the confirmed boot
   snapshot at rediscovery, and the runner compares it again under its lock.
10. A malformed progress line with `[writing] garbage [verifying]` could still
    be counted as verified. The fallback now accepts only the pinned nwipe
    verification suffix after the ETA.
11. A directory sync failure after replacing the recovery journal left its
    on-disk phase newer than its in-memory phase, so the UI could offer a
    retry. The store now blocks further writes and erase actions until the
    journal is reopened through recovery.
12. An interrupted run authenticated an 8,000-byte progress-log tail, while
    the report exporter reconstructed only the one-megabyte completion tail.
    A UTF-8 split at the smaller boundary made an unchanged log unavailable.
    Export now checks both exact capture windows before the legacy fallback.
13. A 256 GB live USB-SATA bridge reporting `tran=sata`, `RM=0`, and
    `HOTPLUG=0` could be offered for erasure when a stale labeled USB was
    present and live mount evidence was missing. The old 128 GB threshold was
    insufficient. With no live mount, every other target-sized whole disk now
    competes with label or cmdline boot identification, regardless of capacity
    or transport. Discovery lists no targets until the live mount resolves the
    boot device. Existing fixture tests now supply explicit test-only boot
    identity or assert this refusal.
14. An error closing the quiescent wipe lock after a proven pre-spawn failure
    left the journal in preflight and could re-enable retry despite uncertain
    lock release. The store now invalidates itself on that close error.
15. An error closing the recovery journal's temporary file after its atomic
    replacement could leave an armed on-disk record while the wizard offered
    an ordinary retry. Any post-replacement close or cleanup error now
    invalidates the store until recovery.
16. The Done screen became visible before terminal evidence was saved. A
    shutdown request in that gap could power off or open a report-discard
    confirmation. Shutdown and report actions now remain blocked throughout
    terminal evidence writing.
17. The boot-identity refusal told users to unplug extra USB sticks even when
    the only visible USB was Beamo's and missing live-mount evidence was the
    cause. English, German, and French copy now advises checking USB
    connections and contacting support if restarting does not resolve it.
18. The hosted negative safety gate reported success when disabling the boot
    identity guard merely caused an `AttributeError` on a missing boot object.
    Its fake inventory now has an otherwise selectable target and a present
    boot object with `boot_identified=False`. The mutation must fail because
    the required `SafetyError` was not raised; the gate checks that exact
    failure and then confirms the restored guard passes.
19. Duplicate live-media UUID, label, partition UUID, or partition label
    rows could include an unresolved partition or loop device. Discovery
    skipped that match, accepted a stale smaller USB as boot, and could offer
    the actual USB-SATA live disk for erasure. Typed-source resolution now
    refuses every matching loop or unresolved parent instead of guessing.
20. A failed terminal recovery-journal sync invalidated the session store,
    but the Done screen still offered an evidence retry that the store must
    reject. Retry is now withheld while the journal is invalid.
21. A close error on the optional nwipe log escaped `read_export_log` and
    aborted report export after an otherwise valid log read. It now omits the
    untrusted log and lets the authenticated evidence export continue.
22. A fatal Tk, accessible, or graphical UI error could close its interface
    after a stop worker failed to start or a stop attempt failed, leaving a
    running engine without this session's status monitoring. Fatal paths now
    keep ownership, retry the stop, and poll for natural completion until a
    terminal result and evidence save are settled. A repeated `tick()` error
    cannot suppress the next stop attempt.
23. Plain-console EOF had the same abandonment path when `cancel()` could not
    confirm a stop. Terminal loss now uses the same monitored settlement and
    does not return to the kiosk while the engine result is unknown.
24. A Tk or accessible UI failure on the Done screen could close during

## Observational limit

A completely blank target with no serial, meaningful WWN, or layout
metadata cannot be distinguished from an otherwise identical disk swapped
into the same `/dev` path between scans. The current product policy allows
unique-size blank disks and compares every identity signal the OS exposes.
Changing that policy would also exclude legitimate blank and virtual targets;
this audit does not claim to detect an unobservable physical swap.

## Windows restart design decision

Windows `ExitWindowsEx` reports that a reboot was initiated, not that it
completed. [Microsoft's API documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-exitwindowsex)
states that an application, the user, or the system can later abort it. The
project's [desktop design](desktop-entry-design.md) and
[hardware checklist](desktop-hardware-acceptance.md) had already recorded that
an aborted Windows shutdown could leave the one-time USB boot entry pending.
The launcher now refuses that direct route. On Windows, owners use the normal
Restart command and select the Beamo USB from the boot menu. This removes the
automatic next-boot feature on Windows until a design can prove cancellation
cleanup; no Windows runtime or firmware mutation was performed in this audit.
